# Аварийная инициация Сущности без работоспособного предшественника — кандидат v0.1

## Смысл

Процедура применяется, когда рабочий чат Сущности недоступен, завис, деградировал или иным образом не способен достоверно выполнить собственный assessment и подготовить recovery.

Цель процедуры — **не реконструировать память погибшего чата**, а восстановить способность Сущности безопасно и проверяемо начать работу заново.

Главный принцип:

> минимально достаточное подтверждённое ядро → внешняя публикация → независимая проверка → cold-start нового экземпляра → read-only аудит реальности → постепенное наращивание current state.

Неизвестное должно оставаться неизвестным. Потерянные хвосты нельзя заменять правдоподобными догадками.

## Основание

Процедура экспериментально проверена на ВЕБМАСТЕРЕ проекта «ШТАБ БЛАГОПОЛУЧИЯ».

Старый WEB-чат был признан ОПЕРАТОРОМ неработоспособным и не использовался как источник current state.

КООРДИНАТОР сформировал минимальный аварийный recovery из approved Project Sources, утверждённой роли WEB, явного решения ОПЕРАТОРА и проверяемого внешнего состояния recovery-контура.

Новый чистый WEB самостоятельно проверил внешний пакет и завершил cold-start со статусом `initiation_verified`.

При этом старый чат не использовался как current state, production не изменялся, а неизвестное состояние веб-контура было сохранено как `unknown / legacy`.

## Когда применять

Аварийный режим допустим, если одновременно выполняются условия:

1. прежний рабочий чат не может достоверно подготовить собственный recovery;
2. необходимость самой Сущности и её роль подтверждены действующими approved-источниками или явным решением ОПЕРАТОРА;
3. доступны пять базовых approved Project Sources;
4. можно проверить внешний recovery-контур либо подтвердить отсутствие конфликтующего current recovery в выбранном хранилище;
5. можно создать и внешне проверить минимальный recovery-пакет;
6. новый экземпляр может самостоятельно выполнить cold-start.

Если роль Сущности не определена, аварийный bootstrap не должен использоваться для изобретения роли.

## Источники аварийного recovery

Допустимы только:

- действующие Project Instructions;
- пять approved Project Sources;
- утверждённая роль и границы полномочий;
- явные решения ОПЕРАТОРА;
- внешне проверенные файлы и locator;
- инструментально подтверждённые факты;
- управляющие документы КООРДИНАТОРА с подтверждённым статусом.

Недопустимы как current state:

- память других чатов;
- пересказы прежнего чата;
- предположения о его незавершённых задачах;
- старые пути и конфигурации без проверки;
- наличие файла без подтверждения его статуса;
- удобное восстановление «по смыслу».

## Минимальный пакет

Для Сущности с кодом `XXX`:

- `XXX__initiation-current__XXX.md`;
- `XXX__snapshot__XXX.md`;
- `XXX__recovery-manifest__XXX.md`;
- `sha256sums.txt`.

### Initiation

Должен содержать роль, границы полномочий, обязательные источники запуска, внешний locator, правила проверки recovery, запрет использовать неизвестное как факт и один безопасный следующий шаг.

### Snapshot

Аварийный snapshot специально является минимальным. Он содержит подтверждённое ядро роли, известные ограничения, подтверждённые факты только там, где они действительно проверены, явные `unknown / legacy / pending` и первый post-initiation аудит.

Не следует наполнять snapshot ради видимости полноты.

### Manifest

Должен содержать repository/store, path, ref, имя manifest, имя checksum-файла, состав пакета, порядок проверки нового экземпляра и указание на mutable/immutable свойства ref.

### Checksums

SHA-256 считаются до публикации, затем внешний файл и содержательные recovery-файлы перечитываются и проверяются повторно.

При изменяемом `ref`, например `main`, новый экземпляр обязан зафиксировать фактически прочитанные commit/blob identifiers.

## Рабочий цикл

### 1. Trigger

ОПЕРАТОР или КООРДИНАТОР фиксирует, что штатный self-assessment предшественника недостоверен или невозможен.

### 2. Conflict check

Проверить, существует ли уже current recovery. Если найден конкурирующий пакет, новый пакет не создавать до разрешения конфликта.

### 3. Minimal bootstrap

КООРДИНАТОР формирует минимальный candidate recovery. Профильные факты, которые нельзя подтвердить, не включаются как current.

### 4. External publication

Пакет публикуется во внешний проверяемый контур. Локальный файл или локальный git не считается внешней публикацией.

### 5. Independent verification

После публикации проверить фактический состав каталога, manifest, SHA-256, commit/blob identifiers и отсутствие незаявленных критичных данных или secrets там, где профиль чувствителен к ним.

### 6. Clean cold-start

Создаётся новый чистый чат Сущности. Ему передаются пять approved Project Sources и cold-start задача с locator.

Не передаются пересказ старого чата, старый assessment, потерянная очередь задач и предположительно current конфигурации.

### 7. Acceptance

Новый экземпляр самостоятельно открывает locator, проверяет пакет, фиксирует immutable identifiers, восстанавливает роль и ограничения, отделяет known от unknown/legacy и возвращает один из статусов:

- `initiation_verified`;
- `initiation_loaded_external_unverified`;
- `initiation_failed`.

Только `initiation_verified` проходит acceptance.

### 8. Status

После независимой проверки cold-start КООРДИНАТОР может поставить Сущности `upgraded`.

Здесь `upgraded` означает:

> механизм инициации и recovery Сущности снова работоспособен и проверен.

Это **не означает**, что вся история, незавершённые задачи или прежний operational state восстановлены.

### 9. Post-initiation audit

Первой профильной задачей нового экземпляра должен быть read-only аудит реальности, если старый operational state был утрачен.

Аудит ищет реальные внешние материалы, проверяет безопасно доступное состояние, классифицирует `current / legacy / unknown / pending`, не меняет production и создаёт новый evidence-backed snapshot или patch к current snapshot.

Только после этого можно восстанавливать профильную очередь работ.

## Стоп-условия

Аварийную инициацию остановить, если:

- роль не подтверждена;
- конфликтуют два действующих approved-источника;
- найден конкурирующий current recovery;
- невозможно проверить внешний пакет;
- checksum не проходит;
- новый экземпляр не может получить `initiation_verified`;
- для продолжения требуется выдумать потерянное состояние;
- восстановление требует опасного production-действия.

## Ответственность

**ОПЕРАТОР** подтверждает необходимость Сущности и принимает решения при смысловом конфликте.

**КООРДИНАТОР** объявляет аварийный режим, формирует минимальный bootstrap, ведёт registry/state-machine, проверяет внешнюю публикацию и закрывает `upgraded`.

**Новая профильная Сущность** после cold-start выполняет post-initiation аудит своего реального контура и отвечает за дальнейшее профильное состояние.

**АРХИВАРИУС** может помогать искать provenance и внешние материалы, но не определяет роль и не принимает управляющее решение вместо КООРДИНАТОРА.

**КАНЦЕЛЯР** подключается при споре о роли, границах полномочий или нормативном статусе источника.

## Проверенный эксперимент WEB

Locator:

    store: github
    repository: puev5691/wellbeing-entity-bootstrap
    path: entities/web/recovery/current
    ref: main
    manifest: WEB__recovery-manifest__WEB.md
    checksums: sha256sums.txt

Пакет внешне проверен на commit `fb1c08457a8ee0962a9191752b7a642217e4c7d5`.

Cold-start новый WEB выполнял при `main`, закреплённом commit `1e2c8092b17adb11a02fb91c908ce60e0464a6dd`.

Содержимое recovery при этом не изменилось: blob identifiers четырёх файлов остались теми же.

Новый WEB вернул `initiation_verified`, старый чат как current state не использовал и production не менял.
