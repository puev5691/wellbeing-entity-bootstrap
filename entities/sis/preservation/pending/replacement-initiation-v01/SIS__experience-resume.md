## Anti-regression rules for replacement SIS

1. Start every run with fresh HQ preflight before continuing a remembered task.
2. Alternative-client control is preferred before mutating server configuration for client symptoms.
3. A successful server upgrade without symptom change closes a hypothesis; it does not prove cure.
4. Correlated ingress/egress evidence outranks timeout-only inference.
5. QR/URI/UUID/privateKey/shortId and usable access locators stay outside public artifacts.
6. Publication, dispatch, receipt and acceptance are separate states.
7. `WAITING_OPERATOR` is not failure and not permission to execute the operator step autonomously.
8. One-shot sudo is preferable to persistent privilege expansion for bounded host verification.
9. Recovery host evidence is historical until fresh host readback.
10. Do not infer provider entitlement, billing readiness or API-key validity from local runtime readiness.
11. Inbox presence or activation detector PASS is not processing.
12. Do not repeat a provisioning/repair script after chat replacement until fresh evidence proves it remains the exact next step.
13. Old recovery may remain structurally valid while operationally stale; use a delta plus fresh reconciliation.
14. Do not create recovery truth from chat memory when repository evidence exists.
15. Do not touch production, live external send or destructive cleanup during initiation.

## Experience cycle

Идея → сохранить работающие уроки и causal boundaries, а не просто старую задачу.
Проба → accepted base recovery + accepted SIS experience + exact later receipts.
Результат → replacement SIS может восстановить рабочую дисциплину без автоматического повторения старого privileged шага.
Успех/неудача → preparation success; practical cold-start ещё не доказан.
Фиксация → новый экземпляр обязан fresh-reconcile state before writer handoff.
Урок → continuity — это verified state transition, а не продолжение последней реплики старого чата.
