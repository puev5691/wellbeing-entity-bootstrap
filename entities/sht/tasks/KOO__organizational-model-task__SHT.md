# ШТАБИСТУ: организационная модель общей среды Сущностей

## Назначение

КАНЦЕЛЯР подготовил кандидат смыслового фундамента общей среды Сущностей:

`KAN__entity-environment-semantic-foundation-v01-candidate__KOO.md`

КООРДИНАТОР принимает его как **рабочую смысловую основу следующего слоя**, но не как approved-канон.

Твоя задача — не переписывать словарь и не проектировать программный протокол, а превратить понятийную модель в **организационную модель жизни системы**:

> кто инициирует действие → кто получает → кто принимает → кто исполняет → как фиксируется состояние → как работают зависимости → когда требуется КООРДИНАТОР → когда требуется ОПЕРАТОР.

## Статус роли в этой задаче

ШТАБИСТ пока не имеет завершённого current recovery/профильного переоформления.

По явному решению ОПЕРАТОРА для **этой задачи** ШТАБИСТ используется как внутренняя организационно-процессная Сущность.

Это назначение не должно молча превращаться в окончательное long-term определение роли SHT. Если текущая роль/инициация ШТАБИСТА противоречит этой задаче — остановись и верни КООРДИНАТОРУ конфликт.

Не используй память старого чата как источник истины.

## Исходная смысловая база

Используй:

1. пять действующих approved Project Sources;
2. `KAN__entity-environment-semantic-foundation-v01-candidate__KOO.md`;
3. явные решения ОПЕРАТОРА;
4. действующие подтверждённые роли Сущностей.

Кандидат КАНЦЕЛЯРА сохраняет статус `candidate_for_coordination`.

Не утверждай самостоятельно пункты, которые КАНЦЕЛЯР пометил `needs_decision`.

## Ключевые различения, которые нельзя потерять

Организационная модель обязана сохранять:

- Сущность ≠ экземпляр ≠ чат;
- роль ≠ задача;
- полномочие ≠ техническая capability;
- artifact ≠ message ≠ event ≠ task;
- публикация ≠ доставка ≠ получение ≠ принятие;
- файловое поле ≠ координационное поле;
- snapshot ≠ вечный current;
- historical evidence ≠ live-state;
- `unknown` — допустимое состояние;
- recovery восстанавливает проверяемое состояние, а не скрытую память чата;
- КООРДИНАТОР не является обязательным посредником каждого обмена;
- ОПЕРАТОР не должен быть ручным транспортным протоколом;
- high-impact действие не становится разрешённым из-за наличия инструмента.

## Главная задача

Подготовь кандидат **организационной модели общей среды Сущностей**.

Он должен отвечать на вопрос:

> как система работает в штатном режиме, когда несколько Сущностей самостоятельно обмениваются задачами, событиями и артефактами в пределах своих ролей, а КООРДИНАТОР и ОПЕРАТОР включаются только там, где это действительно требуется.

## 1. Организационные объекты

Для каждого объекта определи:

- кто может создать;
- кто может изменить;
- кто может закрыть;
- кто несёт ответственность;
- какие обязательные состояния он проходит;
- какие переходы запрещены.

Минимальный набор:

- Сущность;
- экземпляр Сущности;
- задача;
- поручение;
- запрос;
- сообщение;
- событие;
- артефакт;
- locator;
- handoff;
- маршрут;
- зависимость;
- lease;
- lock;
- конфликт;
- эскалация;
- approval / принятие результата.

## 2. Жизненные циклы

Нужны отдельные жизненные циклы, не один универсальный status-field.

Минимум:

### Задача

Пример направления для анализа:

`created → routed → received → accepted → leased/active → result_ready → delivered → accepted_result → closed`

Не принимать этот пример автоматически. Построй собственную модель и объясни переходы.

Различить:

- доставку задачи;
- получение задачи;
- принятие в работу;
- фактическое исполнение;
- готовность результата;
- доставку результата;
- содержательное принятие результата;
- закрытие.

### Артефакт

Различить:

- created;
- local;
- externally_published;
- version_identified;
- delivered;
- received;
- accepted/rejected/superseded;
- archived/legacy.

### Событие

Определи:

- кто публикует;
- является ли событие только фактом;
- когда событие автоматически порождает задачу;
- когда требуется подписка;
- как исключить повторное исполнение одного события.

### Экземпляр Сущности

Минимально рассмотреть:

- uninitiated;
- initiating;
- verified;
- active;
- degraded;
- unavailable;
- retired.

Связать с recovery, но не переписывать recovery canon.

## 3. Прямое взаимодействие Сущность ↔ Сущность

Определи штатный контур, в котором КООРДИНАТОР не нужен как посредник.

Нужно установить:

- кто может обратиться к кому;
- какой объект взаимодействия допустим;
- когда получатель обязан принять сообщение, но не обязан принимать задачу;
- когда задача может быть принята напрямую;
- когда требуется возврат к КООРДИНАТОРУ;
- как фиксируется отказ;
- как предотвращать «самоназначение» чужой работы;
- как не допустить взаимного бесконтрольного делегирования.

## 4. Роль КООРДИНАТОРА

Сформулируй организационно, а не технически.

КООРДИНАТОР должен включаться как минимум при:

- конфликте приоритетов;
- неизвестном исполнителе;
- нескольких конкурирующих исполнителях;
- межконтурной зависимости;
- споре о роли;
- необходимости нового полномочия;
- изменении общей нормы;
- конфликте целей;
- эскалации ОПЕРАТОРУ.

Проверь, можно ли часть этих случаев разрешать автоматически существующим правилом без участия KOO.

Цель: КООРДИНАТОР — **арбитр и управляющий контур**, а не центральный диспетчер каждого сообщения.

## 5. Роль ОПЕРАТОРА

Определи организационный принцип человеческого участия.

Не составлять пока детальный safety-policy.

Нужно разделить:

- действия, которые Сущности могут выполнять постоянно;
- действия по standing delegation (заранее ограниченному полномочию);
- действия, требующие разового approval;
- действия, которые нельзя делегировать автономно.

Используй предложенную КАНЦЕЛЯРОМ шкалу A0–A7 как материал для анализа, но не объявляй её утверждённой permission matrix.

## 6. Несколько экземпляров одной Сущности

КАНЦЕЛЯР оставил вопрос `needs_decision`.

Проработай организационные варианты:

### Вариант A
Один активный экземпляр на Сущность.

### Вариант B
Несколько экземпляров, но один current-writer.

### Вариант C
Несколько параллельных экземпляров с lease/lock.

### Вариант D
Несколько экземпляров по подролям/воркерам.

Для каждого:

- преимущества;
- риски;
- требования к координации;
- риск расхождения состояния;
- пригодность для нынешнего проекта.

Дай рекомендацию КООРДИНАТОРУ, но не превращай её в норму.

## 7. Файловое поле и доставка

КАНЦЕЛЯР правильно зафиксировал конфликт с действующим файловым каноном.

Организационно проработай будущую схему:

> артефакт опубликован во внешнем файловом поле → адресату передан locator → адресат подтвердил получение → результат принят/отклонён.

Нужно определить:

- какое событие начинает маршрут;
- что является доказательством доставки;
- что является доказательством получения;
- кто подтверждает принятие;
- когда маршрут можно закрыть;
- как обрабатывается недоступный locator;
- как обрабатывается изменяемый `main`;
- должен ли адресат фиксировать immutable version;
- что делать, если file field доступен, но coordination field недоступен.

Не отменяй текущий approved-канон. Результат должен содержать **предлагаемую организационную поправку**, которую потом можно передать КАНЦЕЛЯРУ на нормативное оформление.

## 8. Координационное поле

Опиши **минимальный организационный набор примитивов**, без выбора технологий.

Для каждого указать назначение и обязательные поля на смысловом уровне.

Минимум:

- message;
- task;
- event;
- acknowledgement;
- dependency;
- subscription;
- lease;
- lock;
- escalation;
- artifact reference.

Не проектировать JSON/API.

## 9. Отказ, ошибка и недоступность

Система должна штатно переживать:

- экземпляр не отвечает;
- артефакт недоступен;
- locator устарел;
- задача зависла;
- lease истёк;
- два экземпляра взяли одну задачу;
- результат противоречит текущему state;
- Сущность считает задачу вне своей роли;
- КООРДИНАТОР недоступен;
- ОПЕРАТОР недоступен;
- два approved-источника конфликтуют.

Нужно определить организационную реакцию и точку эскалации.

## 10. Организационные инварианты

Из смысловых инвариантов КАНЦЕЛЯРА выдели набор **процессных инвариантов**.

Например:

- задача не может быть `closed`, если результат не существует либо отказ не зафиксирован;
- lease не меняет роль и полномочия;
- acknowledgement не означает acceptance;
- публикация события не означает разрешение на действие;
- если задача вне роли, исполнитель не «расширяет себя», а возвращает/эскалирует её.

Примеры проверить и сформулировать собственную версию.
