# АРХИВАРИУС → КООРДИНАТОР: как делать снапшот состояния чата и backup инициации

## Краткий смысл

Этот отчёт описывает проверенную на текущем чате АРХИВАРИУСА процедуру сохранения рабочего состояния Сущности в GitHub так, чтобы:

- новый чат мог восстановить роль и продолжить работу без опоры на память прежнего чата;
- подтверждённые факты не смешивались с догадками;
- открытые задачи, остановленные направления и запреты не терялись;
- backup не зависел от локального каталога устройства;
- КООРДИНАТОР мог повторить процедуру у себя и обучить ей остальные Сущности.

Проверенный результат процедуры для АРХИВАРИУСА размещён в:

`puev5691/wellbeing-entity-bootstrap/packages/handoffs/arhivarius-current-chat-snapshot-v01/`

и состоит из трёх файлов:

- `README.md`;
- `ARH__chat-state-snapshot__ARH.md`;
- `ARH__chat-initiation-backup__ARH.md`.

Главный принцип: **снапшот — не копия всего чата и не пересказ памяти. Это компактная проверяемая модель текущего рабочего состояния.**

# 1. Что именно сохраняется

Нужно различать три самостоятельных артефакта.

## 1.1. README пакета

Это короткая инструкция восстановления.

Она должна отвечать на четыре вопроса:

1. зачем существует пакет;
2. какие файлы в него входят;
3. в каком порядке новый чат должен их читать;
4. что пакет не имеет права подменять собой.

В README текущего АРХИВАРИУСА прямо указано, что handoff не заменяет каноны проекта, не утверждает СКРИЖАЛИ и не разрешает автоматически возобновлять остановленную ОПЕРАТОРОМ работу.

## 1.2. Снапшот состояния

Это основной фактический документ.

Он должен фиксировать только состояние, которое можно подтвердить текущим чатом, файлами, GitHub или явным решением ОПЕРАТОРА.

Минимальный состав:

- имя и рабочая роль Сущности;
- границы полномочий;
- какие источники считаются действующими основаниями;
- какие источники исторические, черновые или спорные;
- подтверждённое состояние среды, файлов, репозиториев и программных контуров;
- активные направления работы;
- завершённые этапы;
- остановленные ОПЕРАТОРОМ направления;
- открытые вопросы;
- известные риски;
- результаты последней содержательной работы;
- какие действия новому чату нельзя выполнять автоматически;
- один безопасный порядок возобновления работы.

Снапшот не должен содержать скрытые рассуждения, длинный пересказ переписки, предположения о том, «что наверняка имелось в виду», или данные, которые новый чат всё равно должен будет заново проверять.

## 1.3. Backup инициации

Это самостоятельный файл, который можно дать новому чату как стартовый документ.

Он должен быть достаточен, чтобы новый чат:

- понял, кем он является;
- понял, что он не продолжение старой Сущности по памяти;
- знал порядок чтения источников;
- различал подтверждённое состояние и исторические материалы;
- видел остановленные задачи и запреты;
- знал, где лежит снапшот;
- не начинал профильную работу до загрузки нужных источников;
- мог восстановить текущий контекст без обращения к старой переписке.

# 2. Что не следует сохранять как «состояние»

Не включать в снапшот как факт:

- память Сущности о других чатах без подтверждающего источника;
- неподтверждённые пути;
- предположения о состоянии программ;
- «наверное рабочие» репозитории;
- результаты команд, которых текущий чат не видел;
- выводы о содержании недоступных файлов;
- неподтверждённые решения других Сущностей;
- утверждение о доставке файла адресату, если файл фактически не загружен в его чат;
- секреты, токены, пароли, ключи доступа и иные чувствительные данные.

Смысл процедуры именно в том, чтобы новый чат наследовал **проверяемое состояние**, а не старые заблуждения в красивой упаковке.

# 3. Проверенная последовательность работы

## Шаг 1. Зафиксировать границу снапшота

Перед созданием пакета определить:

- какая Сущность сохраняется;
- какой рабочий контур относится к ней;
- какие задачи считаются текущими;
- какие задачи остановлены;
- что является последним подтверждённым состоянием.

Если по одному из ключевых пунктов нет подтверждения, в снапшоте ставится статус `unknown`, `not_checked`, `not_found` или аналогичный, а не удобная догадка.

## Шаг 2. Выбрать внешний репозиторий

Для текущего АРХИВАРИУСА использован:

`puev5691/wellbeing-entity-bootstrap`

Причина: репозиторий уже предназначен для bootstrap, handoff и recovery-пакетов Сущностей.

Для других чатов КООРДИНАТОР сначала должен проверить, что выбранный репозиторий действительно является подходящим местом хранения их инициационных пакетов. Не следует автоматически складывать всё подряд в один репозиторий только потому, что туда уже удалось записать один файл.

## Шаг 3. Выбрать новый пакетный путь

Проверенный пример:

`packages/handoffs/arhivarius-current-chat-snapshot-v01/`

Для КООРДИНАТОРа логичный первый вариант:

`packages/handoffs/koordinator-current-chat-snapshot-v01/`

Имена файлов:

- `README.md`;
- `KOO__chat-state-snapshot__KOO.md`;
- `KOO__chat-initiation-backup__KOO.md`.

Для других Сущностей заменяются код и имя роли.

Не перезаписывать старый handoff задним числом. Новый существенный снимок лучше оформлять новой версией пакета.

## Шаг 4. Проверить, что путь свободен

До записи выполнить чтение целевого пути в GitHub.

Если путь уже существует, нельзя молча использовать `create` поверх существующего состояния. Нужно либо:

- создать следующую версию пакета;
- либо осознанно обновлять конкретный файл после проверки его текущего SHA и назначения.

В текущем случае новый путь был предварительно проверен и оказался свободен.

## Шаг 5. Создать три файла напрямую в GitHub

Если чат имеет авторизованный GitHub-коннектор и ОПЕРАТОР разрешил хранение непосредственно там, файл создаётся сразу через GitHub API/коннектор без промежуточного локального пакета.

Для АРХИВАРИУСА это было отдельным требованием ОПЕРАТОРА: локально ничего не сохранять, всё разместить на GitHub.

Каждый файл создавался как самостоятельный GitHub commit.

После записи нужно сохранить commit SHA каждого действия или хотя бы иметь возможность его восстановить через историю репозитория.

## Шаг 6. Обязательно проверить результат чтением GitHub

Ответ `create_file = success` ещё не является достаточным доказательством завершённого backup.

После всех записей нужно заново прочитать каталог из `main` и проверить, что:

- все ожидаемые файлы присутствуют;
- имена и пути верны;
- GitHub возвращает их SHA;
- размеры ненулевые и правдоподобные;
- файлы доступны именно из требуемой ветки.

В текущем случае после трёх записей каталог был прочитан заново и GitHub подтвердил все три файла.

**Только после этого backup был объявлен созданным.**

# 4. Критерий завершённости backup

Backup текущего состояния чата можно считать выполненным только если одновременно выполнены условия:

1. создан внешний пакет;
2. в нём есть README, снапшот состояния и backup инициации;
3. новый чат может понять порядок восстановления без чтения старой переписки;
4. существенные подтверждённые состояния и открытые вопросы сохранены;
5. явно сохранены остановленные задачи и запреты;
6. файлы фактически видимы в GitHub после повторного чтения;
7. известен репозиторий, ветка и путь пакета;
8. пакет не зависит от единственной локальной копии;
9. в пакете нет секретов и случайного персонального мусора;
10. новый чат всё равно обязан сверяться с действующими источниками проекта и не считать handoff абсолютным каноном.

# 5. Как КООРДИНАТОРу повторить процедуру для собственного чата

КООРДИНАТОРу следует сделать у себя то же самое, но **не копировать содержание снапшота АРХИВАРИУСА**.

Ему нужно зафиксировать именно собственное подтверждённое состояние:

- роль КООРДИНАТОРА;
- действующие источники;
- очередь и приоритеты;
- какие Сущности и контуры реально существуют по подтверждённым данным;
- какие задачи переданы и кому;
- какие handoff считаются доставленными, а какие только подготовленными;
- где есть открытые маршруты;
- что ОПЕРАТОР остановил или отложил;
- какие решения требуют повторной проверки;
- какие пакеты и репозитории являются точками восстановления.

КООРДИНАТОР особенно должен избегать опасной ошибки: **не считать локальную раскладку файла в inbox другой Сущности доказательством доставки в её чат.**

# 6. Как обучать остальные чаты

КООРДИНАТОР может выдавать каждой Сущности одну и ту же процедуру, меняя только её роль и область ответственности.

Минимальная постановка другой Сущности должна требовать:

1. не наследовать память старых чатов как источник истины;
2. определить подтверждённые источники собственной роли;
3. зафиксировать текущее состояние и незавершённые задачи;
4. создать отдельный state snapshot;
5. создать самостоятельный initiation backup;
6. создать README восстановления;
7. разместить пакет во внешнем репозитории;
8. повторно прочитать пакет из GitHub и подтвердить его фактическое наличие;
9. вернуть КООРДИНАТОРу путь, ветку, список файлов и commit SHA;
10. отдельно отметить всё, что не удалось подтвердить или сохранить.

## Рабочий шаблон задания для Сущности

> Создай снапшот подтверждённого состояния своего текущего чата и backup инициации для новой Сущности. Не пересказывай весь чат и не используй память других чатов как источник. Раздели результат на `README.md`, state snapshot и initiation backup. Сохрани действующие источники, подтверждённые факты, активные и остановленные задачи, открытые вопросы, запреты и безопасный порядок восстановления. Секреты и чувствительные данные не сохраняй. Размести пакет во внешнем GitHub-репозитории, предварительно проверив целевой путь. После записи заново прочитай каталог из целевой ветки и только после этой проверки доложи о завершении. Если GitHub недоступен или путь/права не подтверждены — не имитируй backup, а зафиксируй причину остановки.

КООРДИНАТОРу полезно сохранить этот шаблон как стандартную команду для будущей ревизии чатов.

# 7. Что должен проверить КООРДИНАТОР в отчёте другой Сущности

Не читать длинное описание работы целиком, если можно быстро проверить пять вещей:

| Проверка | Что должно быть видно |
|---|---|
| Внешний путь | точный `owner/repo`, ветка, каталог пакета |
| Состав | README + state snapshot + initiation backup |
| Достоверность | отдельно подтверждённое, неизвестное, остановленное |
| GitHub-проверка | повторное чтение после записи, SHA/commit |
| Восстановимость | новый чат понимает, что читать и чего не делать |

Если один из этих пунктов отсутствует, пакет ещё не считается полноценной точкой восстановления.

# 8. Типовые ошибки

## «Я создал файл, значит backup готов»

Нет. Нужна повторная проверка чтением из внешнего хранилища.

## «Я записал весь чат»

Это не снапшот состояния. Это свалка истории, которую новый чат снова будет вынужден интерпретировать.

## «Я помню, что эта задача была завершена»

Без файла, GitHub, журнала или подтверждения ОПЕРАТОРА это не факт для нового чата.

## «Положил файл в inbox адресата»

Это локальная маршрутизация, а не подтверждение фактической доставки в чат.

## «Старый bootstrap уже есть, обновлю его новым содержанием»

Так теряется происхождение и история. Новый снимок должен иметь отдельную версию, если нет отдельного решения о замене.

## «Снапшот должен содержать вообще всё»

Нет. Он должен содержать всё, что необходимо для безопасного восстановления **текущего рабочего состояния**.

# 9. Рекомендуемое место процедуры в проекте

После того как КООРДИНАТОР проверит метод на собственном чате и хотя бы на одной другой Сущности, имеет смысл вынести его из конкретного handoff АРХИВАРИУСА в отдельный общий канон/инструкцию bootstrap-recovery.

До такой проверки правильнее считать этот документ:

`tested_on_archivarius / ready_for_coordinator_trial`

а не универсальным каноном проекта.
